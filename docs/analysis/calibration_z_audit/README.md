# 원본 4점 Z와 수평 Gazebo 배치 조사

원본: `src/janggi/calibration/config/calibration.yaml`. 이 조사는 파일·코드·Git 기록과
오프라인 계산만 사용했다. 로봇이나 카메라 장치를 연결하지 않았고 원본/런타임 보정을 수정하지 않았다.
계산 원본은 `audit.py`, 결과는 `results.json`이다.

## 확인된 수치와 출처

| 지점 | ROS에서 기록한 플랜지 Z mm | 222mm 오프셋의 수직 성분 mm | 저장된 팁 Z mm |
|---|---:|---:|---:|
| top_left | 145.4568 | -221.946466 | -76.490 |
| top_right | 145.2845 | -221.946534 | -76.662 |
| bottom_right | 139.4071 | -221.946492 | -82.539 |
| bottom_left | 139.2086 | -221.946483 | -82.738 |

- 플랜지 Z 범위부터 6.2482mm다. 팁 Z 범위는 6.2480mm다.
- 자세 변화로 인한 오프셋 수직 성분 범위는 **0.000068mm**에 불과하다.
- 파일의 `base_xyz`를 원본 `robot_posx`와 222mm 오프셋으로 재계산한 차이는 최대 0.00065mm다.
  반올림 정밀도와 일치한다. m↔mm 변환에서 10배 차이가 생긴 흔적은 없다.
- 네 점의 수치 데이터는 최초 저장 커밋 `8d8ee75`와 현재 파일이 동일하다.
- `-0.076490m = -76.490mm = -7.6490cm`다. `-7.6cm`와 `-8.2cm`의 차이도 약 6mm다.
  이를 `-7.6mm/-8.2mm`로 바꾸려면 원본 플랜지 측정값과 관계가 달라지므로 근거 없이 소수점을 옮길 수 없다.

따라서 6mm 차이는 카메라 깊이에서 추정하거나 최근 코드가 더한 값이 아니라,
**보정 당시 저장된 로봇 자세 수치에 이미 들어 있던 차이**다.
다만 그 기록이 실제 표면의 높이 차이를 정확히 반영하는지는 독립 검증이 없다.

## 좌표를 기록한 과정

1. 사람이 영상에서 검은 격자의 해당 모서리를 클릭하고 확정한다.
2. 프로그램이 그 픽셀의 왜곡 보정 광선 방향을 계산한다. depth는 참고/교차 검증용이다.
3. 사람이 로봇을 조그 등으로 움직여 같은 점에 팁을 맞춘 뒤 확정한다.
4. `calibrate_board.py::_record_robot`가 `robot.posx()`를 호출한다.
5. `robot_ui.py::Robot.posx()`는 `/dsr01/aux_control/get_current_posx`, `ref=0`(DR_BASE)을
   요청하고 응답의 `[X,Y,Z,A,B,C]`를 가공 없이 읽는다. 드라이버 역시 DRFL 응답을 그대로 전달한다.
6. `calib_math.py::tip_position_m`가 `(플랜지 XYZ + R(ABC) × [0,0,222]) / 1000`을 계산한다.

현재 파일의 `posx_source`는 ROS 서비스다. 숫자 여섯 개를 직접 타이핑하는 별도 `--manual-robot`
모드는 있지만 그 모드는 출처를 `manual input`으로 기록한다. 현재 메타데이터는 그 경로가 아니다.

사람이 정하는 것은 영상 점과 로봇 팁을 놓은 위치·확정 시점이다. 바닥에 실제 접촉했는지,
네 번 모두 동일한 손가락 끝/높이를 사용했는지 판정하는 힘 센서·자동 터치 프로브는 없다.
조그 중 확정하면 정지 후 400ms 대기하지만, 외부에서 이미 움직이는 로봇까지 자동 검증하지는 않는다.

## 6mm의 물리적 원인에 관해 확정할 수 없는 부분

네 점은 로봇 베이스 기준으로 약 0.9796° 기울어진 평면에 가깝다. 그 평면을 제거한
잔차의 Z 범위는 0.1861mm다. 이는 네 점의 수치적 평면성이지 실제 판 중앙의 굴곡 측정값은 아니다.

가능성을 구분해야 한다.

- **평탄도와 좌표계 수평은 다르다.** 판 자체가 평평해도 테이블과 로봇 베이스 축이 상대적으로
  약 1° 기울어져 있으면 로봇 Z에서 6mm 차이가 날 수 있다. 실제로 그런지는 수준기/재측정이 필요하다.
- 현재 베이스 축 기준 실측에서도 높이 차이가 1~2mm뿐이라면, 과거 점의 접촉 높이·시점,
  실제 손가락 길이/접촉 위치 또는 당시 좌표 기준이 현재와 달랐을 가능성을 확인해야 한다.
- 파일은 팁 길이를 **명령 650에서 222mm**라고 설정했지만 각 점의 `gripper_stroke` 기록은
  모두 **700**이다. 당시 코드는 이 불일치를 경고한 뒤 사용자가 계속 기록할 수 있었다.
- 이 `gripper_stroke`는 실제 엔코더 위치가 아니라 그리퍼 노드의 명령 시각화 값이다.
  따라서 네 번 모두 같은 물리 개도로 도착했다는 증거는 아니다.
- 일정한 222mm 오프셋이 틀렸다면 절대 Z 기준은 이동하지만, 같은 자세에서의 **일정한** 오프셋
  오류만으로 상하 6mm 차이가 만들어지지는 않는다. 모든 점이 같은 700이라는 명령 기록만으로
  개도 불일치가 6mm의 원인이었다고 단정할 수도 없다.

당시 실제 접촉 영상, 힘/접촉 기록, 독립적인 평면 실측이 없어 이 중 한 원인을 확정할 수는 없다.
코드에서 확인 가능한 추적의 끝은 서로 다른 플랜지 Z가 기록되었다는 사실이다.

## 왜 화면이나 보정 잔차는 잘 맞을 수 있는가

### 서로 다른 계산 경로

| 용도 | 실제 사용하는 정보 |
|---|---|
| 영상에서 9×10 격자/칸 할당 | 네 모서리 **픽셀**로 구한 호모그래피. 로봇 모서리 Z는 직접 사용하지 않음 |
| 말 높이 시차 근사 보정 | 추정 카메라-판 거리와 말 높이 |
| 픽셀→로봇 3D 좌표 | `T_base_camera`와 `board_plane_base`의 광선-평면 교차 |
| 격자→로봇 좌표 | 네 모서리의 XYZ 이중선형 보간 |
| 현재 집기 최종 Z | 별도 **판 Z=-20mm 고정 + 말별 2/2/3mm**. 과거 모서리 Z는 자동 가산하지 않음 |

카메라-로봇 보정의 PnP에는 로봇에서 기록한 3D 점의 Z가 들어간다.
**RealSense depth Z를 보정 계산에 사용하지 않는다는 것과 로봇 Z를 사용하지 않는다는 것은 다르다.**
원본 depth는 상단 두 점이 null이고 하단 한 점은 1.521m로 기록돼 있어 독립적인 높이 검증 자료로도 충분하지 않다.

### 같은 네 점으로 다시 맞추는 PnP 실험

원본 RealSense SDK deprojection과 같은 소프트웨어 계산으로 정규화 픽셀을 복원하고,
각 변형마다 카메라 자세와 판 평면을 **다시 추정**했다. 실제 보정 파일에는 저장하지 않았다.

| 가상 입력 | 같은 네 점의 판 잔차 RMS mm | 추정 카메라 Z mm |
|---|---:|---:|
| 원본 | 1.9682 | 575.542 |
| 네 모서리 Z를 모두 1/10로 축소 | 1.9795 | 644.874 |
| 네 모서리 Z를 모두 +5mm 이동 | 1.9682 | 580.542 |
| 좌상단 한 점만 +5mm | 2.4216 | 577.310 |

Z를 1/10로 줄여도 피팅 잔차는 거의 같다. 카메라 자세/위치 추정이 함께 변하기 때문이다.
전부 +5mm는 특히 카메라와 판을 함께 이동한 좌표계 이동과 동등하여 거의 같은 영상이 나온다.
낮은 재투영 잔차는 입력한 같은 점에 잘 맞았다는 뜻이지 실제 판 높이나 카메라 절대 위치가 정확하다는 독립 증명이 아니다.

### 파일의 모서리 Z만 고치는 실험은 또 다르다

`corners[].base_xyz`만 수정하고 저장된 `T_base_camera`와 `board_plane_base`를 그대로 두면,
픽셀→3D 경로는 수정한 Z를 읽지 않기 때문에 그대로다. 현재 최종 로봇 Z도 -20 기준으로 덮어쓴다.
현행 코드로 90개 격자 위치에서 중형 말의 집기 목표를 계산한 결과:

| 부분 편집 | 최대 최종 XY 변화 mm | 최종 Z 변화 mm |
|---|---:|---:|
| 모든 모서리 Z +5mm | 0.0855 | 0 |
| 모든 모서리 Z /10 | 0.2040 | 0 |
| 좌상단 Z만 +5mm | 0.0777 | 0 |

이 작은 XY 변화는 BoardGeometry 법선/투영에 남아 있는 영향이다.
서로 다른 부분이 불일치하는 파일을 만든 실험이지 올바른 보정 변경 방법은 아니다.
반대로 **카메라를 고정한 채 실제 광선 교차 평면을 5mm 올리면**, 같은 격자 픽셀의
XY 변화는 최대 약 **2.96mm**였다. Z가 항상 영향이 작거나 무시돼도 된다는 뜻은 아니다.

## Gazebo가 수평인 이유

`simulation_calibration.py::simulation_data`는 원본을 복사한 뒤 아래를 명시적으로 수행한다.

- 기존 판의 XY 중심·격자 모양/크기·yaw는 보존한다.
- `local[:,2] = 0`으로 원래 기울기/미세 비평면 잔차를 제거한다.
- yaw 전용 회전으로 다시 배치하고 법선을 `[0,0,1]`로 바꾼다.
- 받침 -30mm + 판 두께 10mm = 모든 모서리의 판 윗면 **-20mm**로 둔다.
- 새 판의 위치에서 카메라 픽셀과 평면을 다시 만든 별도 `config/gazebo_calibration.yaml`을 사용한다.

이는 앞서 yaw만 남기고 판을 평평하게 놓도록 바꾼 동작이다. 렌더러가 6mm를 못 보여주는 것도,
물리 엔진이 알아서 판을 수평으로 보정한 것도 아니다. 원본 하드웨어 보정과 시뮬레이션 장면이 같은 기울기를 쓰지 않는다.
Gazebo의 영상/격자가 잘 맞는 것도 동일한 파생 장면에서 만든 일관성이지 실물 Z의 검증은 아니다.

## 현재 결론과 검증 방법

6mm는 코드의 소수점 변환 버그가 아니라 원본 플랜지 기록의 차이다. 하지만 이것을 현재 판의
실제 굴곡/기울기라고 확정할 독립 근거도 없다. 현재 명령 판 Z=-20 고정은 유지한다.
원본 Z만 1/10로 수정하거나 자동 높이 보정에 다시 쓰지 않는다.

실제 원인을 가르려면 동일한 개도·동일한 자세·동일한 손가락 끝으로 같은 면을 종이/게이지 방식으로
맞춰 네 모서리의 **raw 플랜지 Z**를 재측정한다. 순서를 바꿔 2~3회 반복하면 접촉/조작 이력을 구분할 수 있다.
그 결과도 6mm라면 판 자체 굴곡보다 베이스-테이블의 상대 수평과 로봇 좌표 모델을 확인해야 한다.
1~2mm라면 과거 측정 조건이 현재와 달랐다는 근거가 된다. 새로 만든 그리퍼 너비/높이 측정 도구는
개도에 따른 길이 차이를 분리하는 데 사용할 수 있다.

재현 (하드웨어 연결 없음):

```bash
janggi/.venv/bin/python docs/analysis/calibration_z_audit/audit.py
```

시스템 Python으로도 실행할 수 있다. RealSense SDK가 없으면 현행 OpenCV 경로를 사용하며,
`results.json`의 normalization 필드에 기록한다. 기록된 SDK/라이브러리 버전에 따라 마지막 소수점은 달라질 수 있다.

# Gazebo 영상의 속도·종류 분류 진단

현재 실행 중인 ROS 토픽에는 도구 환경에서 연결되지 않아, 저장된 `../gazebo_calibrated_scene/camera_rgb.png`와 현재 모델로 비교했다.
이 CPU 실험 수치를 사용자 UI의 GPU/CPU 직접 프로파일로 해석하면 안 된다.

| CPU 스레드 | 위치 YOLO 중앙값 | 말 32개 CNN 중앙값 |
|---|---:|---:|
| 1 | 716ms | 760ms |
| 4 | 288ms | 268ms |
| 8 | 318ms | 374ms |

각 설정에서 준비 실행 후 3회 측정했다. 두 단계는 별도로 측정했으므로 단순 합계가 실제 비동기 UI 프레임 시간이 아니다.
4스레드 조건에서도 YOLO만 약 3.5회/초 수준이며 CNN과 자원을 공유하면 더 느려질 수 있다.
0.1초 재분류 제한은 실행 시작 간격의 하한이다. 실제 CNN 계산이 268ms 걸린다면 이미 100ms보다 길어 이 제한의 효과가 작다.
최근 사용자 Gazebo 렌더러 로그는 `Mesa Intel(R) Graphics (RPL-P)`를 기록했다. CNN 장치는 이 로그로 확인할 수 없다.

## 인식 품질

저장된 장면에서 위치 검출·교차점 할당은 32개였다. 검출 박스 크기는 약 24~38 × 26~41px이다.
UI 판 확대와 CNN 224px 리사이즈는 원본에 없는 글자 정보를 복원하지 않는다.

초기 배치의 수동 라벨을 기준으로, **크기 가중치와 과거 이력을 적용하기 전 CNN 단독**으로 비교했다.

| 입력 조건 | 정답 개수 |
|---|---:|
| 제공 사진에서 원본 해상도로 잘라낸 타이트 윗면 Crop | 3/32 |
| 위 Crop을 28px로 축소했다가 224px로 확대 | 6/32 |
| Gazebo 영상에서 YOLO가 검출한 Crop | 9/32 |
| Gazebo Crop 좌우 반전 | 10/32 |
| Gazebo Crop 상하 반전 | 9/32 |

이는 한 장면·한 Crop 조건의 진단이며 전체 정확도나 실제 UI의 최종 정확도가 아니다.
그럼에도 이번 사진의 현재 Crop 조건에서도 성능이 낮아, 해상도 저하만으로 오분류를 설명할 수 없다.
현재 분류기 학습 데이터는 단일 촬영 영상에서 내보낸 데이터다. 새 사진의 촬영 조건·색·글자 방향·Crop 구성에
대한 일반화 부족이 의심된다. 단순 반전만으로 큰 개선도 없었다.

UI의 `종류 26/32`는 표시 가능한 종류가 있는 객체 수다. 정답 26개를 뜻하지 않는다.
현재 결과에는 높은 신뢰도의 오분류도 포함되므로 표시 신뢰도만 낮추는 것으로 해결할 수 없다.

우선 실제 실행 장치와 구간별 시간을 측정하고, 사진/렌더링 Crop과 학습 데이터의 조건을 비교해 학습 데이터를 보완해야 한다.
RGB만 사용하는 UI를 위해 깊이 영상까지 만드는 현재 Gazebo 구성도 별도 부하다. 실제 병목 여부는 분리 측정해야 한다.
수치 원본: [results.json](results.json).

## RGB 전용 전환 뒤의 실제 수신 비교

같은 5초 구간에 Gazebo 원본과 ROS 토픽을 동시에 구독했다. 진단 구독자에서는 YOLO/CNN을 실행하지 않았다.

| 도구 환경 수신 경로 | 현실 시간 FPS |
|---|---:|
| Gazebo `/janggi_sim/d455f/image` 직접 구독 | 30.18 |
| ROS `/janggi_sim/d455f/color/image_raw` 구독 | 9.45 |

원본 렌더링/발행은 30 FPS에 도달했지만 ROS 경로의 이 수신자는 약 9.45 FPS였다.
`ros_gz_bridge` 변환·DDS/네트워크 전송·rclpy 수신 중 어디서 손실/지연이 생기는지까지는 분리하지 못했다.
최근 렌더러 로그(2026-11-11 21:47:37)는 Intel 내장 그래픽을 기록하며, CNN의 CUDA 사용 여부와는 별개다.
RGB 1280×720×3×30은 약 82.94MB/s의 비압축 픽셀 데이터이며, 중간 복사/변환은 추가 작업이다.

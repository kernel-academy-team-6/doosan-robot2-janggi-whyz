TECHNICAL BRIEF · 01

카메라가 읽고, 엔진이 판단하고, 로봇이 둡니다

Doosan E0509와 ROBOTIS RH-P12-RN-A 그리퍼로 사람과 장기를 두기 위한 ROS 2 Jazzy 기반 통합 워크스페이스입니다. 로봇 드라이버뿐 아니라 영상 수집, 말 검출·분류, 추적, 장기 규칙·엔진, 좌표 보정, 집기·놓기, 평가 도구까지 포함합니다.

입력

RealSense RGB

말의 박스·종류와 장기판 위치를 관측합니다.

판단

판 상태 + 엔진

관측을 게임 상태로 바꾸고 다음 수를 계산합니다.

실행

E0509 + 그리퍼

픽셀·교차점을 로봇 좌표로 변환해 말을 옮깁니다.

읽는 기준: 2026-11-11 작업 트리의 소스와 README를 기준으로 정리했습니다. “포함됨”, “기본 빌드”, “대국 경로에서 사용됨”은 서로 다릅니다. 장비 연결·실제 파지 성능을 이번 문서 작업에서 새로 검증한 것은 아닙니다.
발표 멘트

이 프로젝트는 장기를 잘 두는 AI 하나가 아니라, 실제 장기판의 상태를 읽어 로봇 동작까지 연결하는 인지·판단·제어 시스템입니다.

TECHNICAL BRIEF · 02

전체 아키텍처와 데이터 흐름

카메라는 현재 애플리케이션에서 RealSense SDK로 직접 접근합니다. 초기 설계의 ROS 카메라 토픽 구독을 현재 구현으로 오해하지 않아야 합니다. 게임·추적 로직은 Python 모듈이고, 실제 로봇에 명령을 보낼 때 rclpy로 ROS 2 인터페이스를 사용합니다.

계층핵심 입력 → 출력왜 나누었나
인식RGB 프레임 → bbox, 탐지 확률, 종류 확률위치 검출과 종류 판별을 별도로 개선
추적·판 상태연속 검출 → 객체 ID / 관측 위치 / 확정 위치가림·흔들림이 곧 게임 상태 변화가 되지 않게 처리
게임·엔진인식판 → FEN → 최선수비전·제어와 장기 탐색 분리
좌표·동작픽셀 / 교차점 → base 좌표 / 집기·놓기눈으로 보이는 위치를 실제 도달 위치로 변환
드라이버ROS 서비스·토픽 → 로봇 API / 시리얼장비 통신을 상위 로직에서 분리
초기 설계인 JANGGI_DESIGN.md의 janggi_interfaces / janggi_perception / janggi_executor 패키지 구상, depth 기반 위치 추정, 실행 후 자동 VERIFY는 현재 구현 전체를 그대로 나타내지 않습니다. 현재 코드는 이 문서의 실제 경로를 기준으로 설명합니다.
TECHNICAL BRIEF · 03

한 턴은 어떻게 진행되나요?

순서실제 동작발표에서 짚을 점
① 초기화보정 파일과 모델을 읽고 인식된 판으로 시작위치 전용 모델은 진영·종류가 없으므로 대국 불가
② 사람 착수사람이 수를 두고 착수 완료를 누름손이 사라졌는지 자동 보장하는 시스템이 아님
③ 판 반영RobotGame.apply_human_move()가 비어 있지 않은 인식판을 게임판에 반영한 수 추론은 기보용이며, 이 경로는 사람 수의 합법성을 강제하지 않음
④ 최선수 계산fairy.py가 FEN을 엔진에 전달하고 UCI 수를 변환초가 위쪽이면 엔진 좌표를 위해 판을 180° 회전
⑤ 포획 처리잡는 수면 목적지의 상대 말을 먼저 집어 판 밖에 놓음원래 말 이동 전에 목적지를 비움
⑥ 이동·복귀실제 말 중심을 집고 목적 교차점에 놓은 뒤 홈으로 복귀카메라 시야 확보 후 다음 사람 차례
UI 규칙과 로봇 대국의 차이: rules.py는 UI에서 합법 수·장군·외통 등을 계산합니다. 반면 로봇 세션의 사람 수 반영은 인식 오류 때문에 진행을 막지 않도록 인식판을 그대로 채택합니다. “모든 착수의 합법성을 검증한 뒤 움직인다”고 발표하면 현재 코드와 다릅니다.
발표 멘트

말을 집을 때는 카메라가 본 실제 중심을 쓰고, 놓을 때는 보정된 교차점을 씁니다. 말이 격자 중앙에서 조금 비켜 있어도 집기 오차를 줄이려는 구분입니다.

TECHNICAL BRIEF · 04

비전: 위치·종류·신원을 나누어 처리합니다

실행 모드모델 경로하는 일 / 제한
기본값models/weights.pt현재 1클래스 janggi_dol. 위치·개수·교차점 표시, 대국 비활성화
piecemodels/weights_only_piece.pt위치만 검출. 진영·종류는 미확정
fullmodels/weights_14class.pt한 번의 YOLO 추론으로 위치와 14종 판별
hybrid / cnnweights_only_piece.pt + models/piece_classifier/best.ptYOLO 위치 + MobileNetV3-Small 분류. 14종이 모두 없는 분류기는 로봇 옵션 차단

YOLO는 이미지에서 물체 박스(bounding box)를 찾는 객체 검출 모델입니다. MobileNetV3-Small은 계산량이 비교적 작은 CNN 분류기입니다. 초·한의 7종을 합쳐 14클래스를 사용합니다. 위치와 종류를 분리하면 검출 모델을 유지하며 종류 분류기만 교체·재학습할 수 있습니다.

위치 YOLO는 매 프레임 수행하고, 분류는 별도 스레드에서 수행합니다. 알려진 정상 객체는 기본 0.5초 간격, 미분류 객체는 최신 프레임을 우선합니다. 대기 요청은 최신 하나를 유지하며, 객체별 세대 번호로 오래된 결과 적용을 막습니다. 분류 백엔드는 predict(images) 인터페이스로 교체할 수 있습니다.

표시 / 기법의미
D / CD는 검출 확률, C는 종류 확률. 추적 모드의 C에는 확률 이력·크기 점수가 융합될 수 있음
ROIRegion of Interest. 전체 영상 중 보정된 판 영역에 집중해 처리하는 영역
NMS / IoU겹치는 박스를 줄이는 처리 / 두 박스의 교집합 면적 ÷ 합집합 면적
크기 보조보정된 mm 크기와 정상 관측의 중앙값·MAD를 사용해 종류 확률을 부드럽게 보정
종류 이력기본 과거 80% + 현재 20%. 종류 변경은 연속 관측으로 확인
예비 종류미분류 객체의 CNN 최고 확률 50% 이상이면 임시 표시. 게임 확정 증거와 구분
mm 표시는 말의 정확한 지름이 아니라 검출 박스의 추정 길이입니다. 카메라·판 배치와 해상도·말 높이 가정이 맞아야 합니다. 보정이 없어도 영상 기반 추적·분류는 가능하지만 교차점·게임판·mm 보조는 제한됩니다.
TECHNICAL BRIEF · 05

추적: 잠깐 안 보이는 말과 잡힌 말을 구분합니다

PieceState 하나가 검출 박스, 객체 ID, 종류 확률, 크기 이력, 영상 위치와 게임 위치를 함께 보관합니다. cell은 현재 교차점 할당, confirmed_cell은 게임에서 확인한 위치입니다. 영상 추적과 게임 인덱스가 같은 객체를 참조합니다.

Hungarian algorithm은 여러 객체와 여러 검출 사이의 전체 연결 비용을 최소화하는 일대일 배정 알고리즘입니다. 현재 활성 객체는 높은 신뢰도 검출과 먼저 배정하고, 남은 객체만 낮은 신뢰도 검출과 연결합니다. 낮은 신뢰도 관측은 ID를 유지하는 용도로만 쓰며 새 객체 생성·종류 학습·개수 통계·게임 확정 증거에서는 제외합니다.

상태처리 의도
MOVE이동 중인 말. 위치는 추적하되 종류·크기 이력 갱신은 보류
MISS미검출. 현재 세션의 휴면 객체로 보관하며 포획으로 단정하지 않음
CONF검출·연결 신뢰도가 불충분한 관측. 기존 종류·정상 크기 기준 보존
SIZE정상 크기와 어긋난 부분 박스 등. 잘린 박스로 추적 기준을 축소하지 않음
전역 방해프레임 차이·개수 진동 등을 감지. 정상 객체 분류는 계속하되 게임 이동·포획 확정은 보류
가림 감지는 휴리스틱(경험적 규칙)이며 손 전용 검출이나 안전 센서가 아닙니다. 같은 외형의 말이 완전히 겹치거나 같은 자리에서 교환되면 영상만으로 영구 신원을 보장할 수 없습니다. 휴면 상태는 현재 세션 안에서 보관하며 재실행 시 자동 복원하지 않습니다.
발표 멘트

화면에서 말이 사라졌다는 관측과 실제로 말이 잡혔다는 판단은 다릅니다. 이 구분이 가림이나 손 움직임 때문에 판 전체가 잘못 바뀌는 것을 줄여줍니다.

TECHNICAL BRIEF · 06

좌표 보정: 영상의 픽셀을 로봇의 mm로

나무 장기판에서 깊이(depth)가 불안정했던 관측을 바탕으로, 현재 보정은 깊이에 의존하지 않습니다. 판 네 모서리를 영상 픽셀과 로봇 그리퍼 팁의 base 좌표로 각각 기록하고 PnP를 풉니다. 픽셀에서 나온 광선과 판 평면의 교점으로 3차원 위치를 구합니다.

기법 / 파라미터무엇을 하고 왜 필요한가
카메라 내부 파라미터초점거리·주점·왜곡. 픽셀을 카메라 광선 방향으로 바꾸는 데 사용
PnP · IPPE + LMPerspective-n-Point: 2D-3D 대응점으로 카메라 자세 추정. IPPE로 평면 자세를 풀고 LM으로 오차를 줄임
T_base_camera카메라 좌표를 로봇 base 좌표로 바꾸는 회전 R·이동 t. 보정 데이터는 m 단위
Homography두 평면 사이의 투영 변환. 영상 모서리 → 9×10 격자, 말 높이에 따른 시차도 보정
4점 이중선형 보간로봇으로 실측한 네 모서리 사이를 보간해 놓을 교차점의 base 좌표 계산
TCP / 팁 오프셋Tool Center Point: 도구 끝의 작업 기준점. 제어 목표가 플랜지면 팁까지의 길이 보상 필요
보정: 좌상단 → 우상단 → 우하단 → 좌하단
픽셀 → 왜곡 제거 → 카메라 광선 → R, t 적용 → 판 평면 + 말 높이
교차점 (x:0…8, y:0…9) → 네 base 모서리 보간 → 팁 목표 [mm]
기존 action 경로는 보정 팁 오프셋 약 222mm를 사용합니다. 별도 janggi_pick_place2는 개도에 따른 TCP 길이 모델을 씁니다. 서로 다른 설정을 같은 보정값으로 취급하지 않아야 합니다. 카메라·판 이동, TCP 중복 설정, m/mm 혼용, 개도에 따른 팁 높이가 주요 오차 원인입니다.
TECHNICAL BRIEF · 07

제어: ROS 명령이 팔과 그리퍼에 도달하는 경로

DRFL은 Doosan 로봇 제어용 라이브러리입니다. Modbus RTU는 시리얼 통신에서 주소·기능·데이터·오류검사로 장치를 제어하는 프로토콜입니다. 공식 Jazzy 드라이버에 FlangeSerialOpen / Close / Write / Read 네 서비스를 패치해 플랜지 시리얼로 그리퍼를 제어합니다. Humble 포크 전체를 가져오는 대신 Jazzy 제어 API와의 호환 범위를 작게 유지합니다.

ROS 개념이 저장소의 예사용 목적
Topic/dsr01/gripper/position_cmd, joint_states연속 값 발행·상태 공유. 위치 토픽만으로 파지 성공은 알 수 없음
Service/dsr01/motion/move_line, move_joint, move_stop요청/응답 방식의 개별 명령
Action/janggi_pick_place2/pick, /janggi_tcp_test/test오래 걸리는 작업의 목표·피드백·결과·취소
Namespacedsr01로봇 인터페이스 이름을 묶는 접두어. 같은 이름의 실기·가상 동시 사용 주의

기존 action/mover.py는 현재 팁이 낮으면 상승 → 안전 이동 높이에서 XY 이동 → 목적 높이로 하강하는 직선 서비스 경로입니다. MoveIt 기반 환경 충돌 회피가 기본 대국 경로에 자동 적용되는 것은 아닙니다. 판 표면 아래 목표 거부, 호출 타임아웃, 정지 요청 등 소프트웨어 보호가 있습니다.

TECHNICAL BRIEF · 08

별도 동작 패키지: 실험의 목적과 성공 조건

구성목적 / 사용 이유완료가 의미하는 것
src/janggi/action대국용 BoardMover·PiecePicker. 픽셀 집기·교차점 놓기·판 밖 버리기명령 실행 순서 완료. 실측 파지 센서 기반 확인과 구분

janggi_tcp_test예상 개폐 프로파일에 따라 플랜지 Z를 보상하는 TCP 높이 시험. 코드상 geometry·robot_client 등은 janggi_pick_place2 재사용모델 시간 경과 + 팔 위치 확인. 실측 그리퍼 개도에 의한 폐루프 높이 제어가 아님
src/test교차점 순회, dry-run 좌표 확인대국 전 기하·단순 이동 경로 확인
janggi_pick_place2와 TCP 시험은 기존 gripper_service_node에 위치 명령을 보내는 경로입니다. grip_current_ma나 프로파일 모델 값을 입력해도 실제 장치의 전류·속도 설정이 전송되는 것은 아닙니다. TCP 시험 보고서의 작은 추정 오차는 실제 팁 높이 불변의 증명이 아닙니다. 이 액션들은 현재 RobotGame → PiecePicker 경로를 자동 대체하지 않습니다.

동작 패키지는 real / virtual / mock을 구분합니다. Mock은 순서·기하 계산을 검증하며, 실제 장치 오차를 측정하지 않습니다. TCP 시험은 samples.csv, summary.json, report.html을 기본 /tmp/janggi_tcp_test/ 아래에 저장합니다. 일부 README에는 과거 janggi_pick_place 참조가 남아 있으나, 현재 소스 의존성은 janggi_pick_place2입니다.

모델 선택 분리

Val macro-F1으로 best.pt를 고르고 Test는 이후 평가에 사용합니다. macro-F1은 각 클래스 F1을 같은 비중으로 평균한 값입니다.

32개 검출 비율 ≠ Recall / 정확도. 실제 말 하나를 놓치고 배경 하나를 잘못 검출해도 32개가 됩니다. conf는 모델 확신도이며 정답과 비교한 정확도가 아닙니다. 위치·종류·ID 추적·실제 파지 성능은 각자의 정답 또는 실측으로 평가해야 합니다.

실행 환경·재현성과 핵심 고려사항

비전 venv는 시스템 site-packages 없이 만들어 ROS의 NumPy와 pip 패키지가 섞이는 것을 줄입니다. 보정 venv는 --system-site-packages로 시스템 ROS·NumPy·OpenCV를 재사용하고 SDK만 추가합니다. cam_visualizer도 별도 venv입니다. 실제 로봇 대국 run.sh는 ROS setup을 source한 뒤 비전 venv에서 실행하므로, 이 통합 경로의 라이브러리 호환성은 따로 고려해야 합니다.

질문 대비: 짧게 답하는 핵심 6문항
왜 end-to-end AI 하나로 하지 않나요?
위치, 종류, 장기 탐색, 로봇 기하·제어의 실패 원인이 달라 각 계층을 독립적으로 검증·개선하기 위해서입니다.
왜 RGB-D 카메라인데 depth를 안 쓰나요?
현재 보정은 나무 판에서 depth가 불안정했던 조건 때문에 4점 PnP와 평면 교차를 씁니다. depth는 녹화·시각화·보조 검증 용도로 남아 있습니다.
항상 32개로 맞춰 놓는 건가요?
아닙니다. 추적은 32개 고정·종류별 개수 제약을 강제하지 않습니다. 평가 로그의 기본 기준 개수와 추적 로직을 구분해야 합니다.
MoveIt이 움직임을 모두 계획하나요?
구성 패키지는 포함되지만 현재 대국은 BoardMover가 Doosan motion 서비스를 직접 호출합니다.
액션 success면 실제로 말을 잡은 건가요?
독립 pick_place2의 success는 팔 이동 확인과 그리퍼 명령·대기 완료입니다. 실물 파지 성공을 센서로 확인한 뜻은 아닙니다.
모든 패키지를 실행해야 하나요?
아닙니다. 대국 경로, 독립 시험, 데이터 도구와 다른 로봇용 upstream 구성을 나누어 필요할 때 사용합니다.

실행 예시·용어·확인 근거

아래는 워크스페이스 루트 기준입니다. 발표 시 로봇 없이 원본 녹화 영상으로 비전을 보여주면 동일 장면을 반복해서 비교할 수 있습니다. --source 경로는 보유한 원본 영상으로 바꿉니다.

# 카메라·로봇 없이 위치 검출 재생
./janggi/realtime_ui/run.sh --model-mode piece --source /경로/color.mp4 --playback-fps 30

# 분류기 준비 후, 2단계 분류 + 로그
./janggi/realtime_ui/run.sh --model-mode hybrid --source /경로/color.mp4 --log-counts

# 로그 비교 도구
./tools/run_evaluation_viewer.sh --compare

# 로봇 없는 교차점 목표 확인
./src/test/run_move_example.sh --dry-run

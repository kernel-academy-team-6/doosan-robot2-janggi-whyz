# Gazebo 카메라 영상 녹화

Gazebo와 판·말·카메라가 실행 중인 상태에서 workspace 루트에서 실행한다.
인식 UI는 켜지 않아도 된다. 검출 박스·글씨가 없는 원본 RGB만 저장한다.

```bash
./tools/run_gazebo_recorder.sh --duration 60 --fps 30
```

기본값은 `/janggi_sim/d455f/image`를 **Gazebo Transport로 직접 구독**한다.
ROS 브리지를 거치는 경로는 같은 원본이 발행돼도 전송 환경에서 프레임이 누락될 수 있어 기본으로 사용하지 않는다.
비교가 필요할 때만 `--transport ros`를 지정한다.

출력은 `tools/captures/gazebo_날짜_시각/`에 저장한다.

- `color.mp4`: 30 FPS, 기본 1280×720 원본 RGB
- `frames.csv`: 출력 프레임마다 카메라 시간·수신 번호·중복 여부
- `metadata.json`: 실제 수신 수·큐 누락·사용한 원본 프레임 수·중복 수·실제 녹화 소요 시간
- `calibration.yaml`: 녹화 시점의 시뮬레이션 보정 사본

`--duration`은 **카메라의 Gazebo 시뮬레이션 시간**이다. 60초·30 FPS라면 MP4는 1,800프레임이다.
시뮬레이션이 실시간보다 느리면 현실의 녹화 소요 시간은 60초보다 길어진다.
예를 들어 원본이 시뮬레이션 시간으로 30 FPS, 현실 시간으로 15 FPS에 도착하면 녹화는 약 2분 걸린다.
실제 센서 프레임이 없는 구간은 이전 프레임으로 채우고 CSV와 메타데이터에 중복을 명시한다.
FPS 숫자를 30으로 지정했다고 원본 프레임 30장이 반드시 도착하는 것은 아니다.
카메라 시계가 되돌아가거나 2초 넘게 점프하면 현재 파일을 닫고 오류로 종료한다.
영상이 10초간 끊겨도 파일을 닫아 부분 녹화를 보존한다. Ctrl+C로 중단할 수 있다.

## 수신 경로 비교에서 확인된 사항

첫 ROS 경로 녹화는 60초 파일 1,800프레임 중 고유 수신 프레임 312개, 반복 1,488개였다.
같은 실행의 Gazebo 원본 토픽을 5초간 별도로 측정하면 현실 시간 약 15.48 FPS,
시뮬레이션 시간 약 30.30 FPS였다. 따라서 이 도구 환경에서의 ROS 전달 누락이 컸다.
이는 사용자 UI 처리 단계의 직접 프로파일과는 구분한다.
원본 직접 구독을 기본으로 바꾸고 다시 녹화했으며, 최종 수치는 각 파일의 메타데이터에서 확인한다.

직접 구독한 최종 녹화 `gazebo_20261111_212837_235435`는 1280×720, 30 FPS, 60초, 1,800프레임이며
고유 원본 프레임 1,800개·중복 0개·큐 누락 0개였다. 실제 소요 시간은 약 109초였다.
FFprobe와 첫·중간·마지막 프레임 디코딩으로 확인했다.

재생 시 기존 UI는 영상 옆 `calibration.yaml`을 자동 선택한다. MP4만 다른 폴더로 옮기지 말고
보정 사본도 함께 보관한다. 명시적인 `--calibration`이 있으면 그 파일이 우선이다.
기본 녹화 경로는 RGB뿐 아니라 CameraInfo도 Gazebo에서 직접 받아 ROS 영상 브리지 없이 동작한다.
